# make:domain:migrate

[Docs](../README.md) · CLI scaffolding

Sets up migrations for a domain that has none: the migration package, the
bootstrap SQL and the DI registration. It also enables `config/service/sql` and
`config/tools/migrate`, the database and the `migrate` command the runner needs.

## Usage

```sh
waffle make:domain:migrate <name>
```

**In the ordinary flow you never run this.** `make:domain` and
`make:domain:entity` both set the runner up and add the entity's table, and both
are idempotent about it — the runner is recognised by the files already there
rather than by a name that carries a timestamp.

What it is for is the domain that was made with `--no-repository` and now wants a
schema without one. Run it, and the table it starts with is the domain's own
entity.

## Generated files

### Migration package

**`domain/user/cmd/migrate/main.go`**

The migration package exports a `NewMigrations()` constructor that returns the embedded SQL files:

```go
package migrate

import (
    "embed"
)

//go:embed migrations/*
var migrations embed.FS

func NewMigrations() embed.FS {
    return migrations
}
```

The source is reached only through `migrate.MigrationsTag`, so it is registered
with `di.Define` and needs no interface of its own. Each domain still gets a
container field of its own: the field is named after the import alias and the
type, `userMigrationEmbedFS`. A test replaces the sources through the
collection's own `Replacements` field, all at once.

### SQL migrations

**`domain/user/cmd/migrate/migrations/<timestamp>_create_update_at_function.sql`**

A reusable PostgreSQL function that updates the `updated_at` column on any table
that installs the trigger. Every domain scaffolds this file, so the creation is
wrapped in a block that swallows `duplicate_function` — the second domain to be
added finds the function already there. The block is one statement full of
semicolons, which is what `StatementBegin`/`StatementEnd` tell goose:

```sql
-- +goose Up
-- +goose StatementBegin
do $create$
    begin
        create function update_updated_at()
            returns trigger as $trigger$
        begin
            new.updated_at = now();
            return new;
        end;
        $trigger$ language 'plpgsql';

exception
        when duplicate_function then
            null;
    end;
$create$;
-- +goose StatementEnd

-- +goose Down
```

The Down is empty on purpose: dropping the function would break every other
domain's trigger.

**`domain/user/cmd/migrate/migrations/<timestamp>_create_users_table.sql`**

The initial table migration. The timestamp is generated at scaffold time (format `YYYYMMDDHHmmss`; the function above is stamped a second earlier, so it runs first and the two never share a version, which goose refuses). The table name is the plural of the domain name:

```sql
-- +goose Up
create table users (
    id bigint generated by default as identity primary key,
    created_at timestamp(0) with time zone default now() not null,
    updated_at timestamp(0) with time zone default now() not null
);

create trigger users_updated_at
    before update
    on users
    for each row
execute procedure update_updated_at();

-- +goose Down
drop table users;
```

The identity clause matters: the `stored<Entity>` struct marks `id` as
`store:",readonly"`, which keeps it out of the generated `Inserts()` and
`Updates()`, so nothing on the Go side ever supplies a key. `by default` rather
than `always`, so a hand-written insert can still pass one.

Add your domain columns to the Up section before running for the first time.

### DI configuration

**`config/di/di_user_migrate.go`** — written by the command, like every other
registration, so nothing has to be merged into a file you are also editing:

```go
package di

import (
    userMigration "mymodule/domain/user/cmd/migrate"

    "gitlab.com/gorib/di"
    "gitlab.com/gorib/waffle/tools/migrate"
)

func InitUserMigrate() {
    di.Define(userMigration.NewMigrations, di.Tag(migrate.MigrationsTag))
}
```

Nothing calls `InitUserMigrate` — diogen reads the bodies of every `InitXxx` in
`config/di` and never invokes one. See
[di/overview](../di/overview.md#the-initxxx-functions).

## Post-generation steps

```sh
make .tidy generate
```

## Running migrations

```sh
go run ./cmd/app migrate up
```

Or any other goose subcommand through the same binary:

```sh
./app migrate status
./app migrate down
./app migrate up-to 20240315143022
```

The nine of them, the `--connection` override and the fixed `migrations`
tracking table are [tools/migrate](../tools/migrate.md#subcommands).

## Adding new migrations

```sh
waffle make:domain:migration user add_status
```

That writes `domain/user/cmd/migrate/migrations/<timestamp>_add_status.sql`, an
empty `Up`/`Down` pair already wrapped in `StatementBegin`/`StatementEnd` — the
markers a function body or a `$$`-quoted block needs, and the ones people
remember only after goose has split a statement on a semicolon inside one. The
description is a single file-name segment, so it may hold dashes and dots but
not a separator.

By hand is the same file: the convention is `<timestamp>_<description>.sql`, and
the timestamp has to be monotonically increasing — which is the reason to let the
command name it.
